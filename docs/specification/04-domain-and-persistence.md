# 04 — Domain records and persistence

## DATA-001 — Schema notation and scalar types

Every field in this chapter MUST be present unless marked optional. A nullable
field MUST contain null when unknown, not an empty string or invented default.
An empty array means no members. API PATCH omission means unchanged; null means
clear only when nullable. Unknown object properties MUST be rejected on writes.

| Name | Written schema |
|---|---|
| UUID | RFC-form UUID string, generated by the application |
| Instant | UTC ISO-8601 string with milliseconds and Z suffix |
| Revision | Positive integer starting at 1; monotonically increasing per entity |
| Hash | Lowercase SHA-256 hex string, exactly 64 characters |
| URL | Absolute HTTP(S) URL, no userinfo; at most 8192 characters |
| Origin | Scheme, host, effective port only; no path/query/fragment |
| Text | Unicode string; nonempty after trimming unless explicitly allowed empty |
| Ref | Object: id: UUID, revision: Revision |
| Actor | Object: kind: user or worker, id: UUID |
| EvidenceRef | Object: sourceKind: listing/resource/fact/observation, sourceId: UUID, sourceRevision: Revision, segmentId: Text, quote: Text |
| ArtifactRef | Object: artifactId: UUID, sha256: Hash |

All top-level externally exchanged objects MUST carry schemaVersion=1. Database
rows instead use ordered database schema versions. Mutable records have id,
revision, createdAt, updatedAt. Revisioned configuration/content records use a
stable id and immutable (id, revision) versions plus a current-version pointer.
Immutable event/result records have id and createdAt, with no mutable revision.
The tables below list additional fields, not repetitions of these common fields.

Strings MUST have bounded validation: names 200 characters, single reasons 2000,
free-text preferences 8000, extracted document text 1,000,000, and normalized job
description 100,000. IDs, hashes, types, enums, and dates MUST not be model-invented
when they can be assigned or derived by application code.

## DATA-002 — Criteria and normalized job values

Criterion MUST have id: UUID, kind: enum below, strength: required/preferred, and
value with the corresponding type. Search criterion IDs persist across edits so
that UI comparisons remain meaningful. A search has at most one criterion of each
kind; multiple values inside a criterion are alternatives unless noted.

| kind | value schema and meaning |
|---|---|
| title | {titles: Text[1..20], variants: Text[0..40]} |
| arrangement | {anyOf: [full_time/part_time/casual/contract/unspecified]} |
| category | {anyOf: [employment/internship/graduate_program/apprenticeship/unspecified]} |
| weekly_hours | {min: number or null, max: number or null}; at least one bound; 0..168 |
| location | {names: Text[1..20]}; any listed location |
| work_mode | {anyOf: [remote/hybrid/on_site/unspecified]} |
| seniority | {anyOf: [entry/junior/mid/senior/lead/manager/unspecified]} |
| skills | {allOf: Text[1..50]} |
| excluded_terms | {anyOf: Text[1..50]}; any positive occurrence is a violation |
| excluded_employers | {anyOf: Text[1..50]}; normalized exact employer match |
| salary | {min: number or null, max: number or null, currency: ISO-4217 code, period: hour/week/month/year}; at least one bound, nonnegative |
| preferences | {text: Text}; strength MUST be preferred |

Arrays MUST have unique members; enum arrays have at least one member. Ranges
MUST satisfy min <= max when both are known. Unspecified means the site's explicit
classification of unspecified, not permission to treat missing required data as
a match. A listing's absent category is null, not automatically employment.

NormalizedJob MUST contain title: Text, employer: Text or null, location: Text
or null, arrangements: enum[] or null, categories: enum[] or null, workMode: enum
or null, seniority: enum or null, weeklyHours: {min,max} or null, salary:
{min,max,currency,period} or null, skills: Text[], publishedAt: Instant or null,
closesAt: Instant or null, description: Text, and evidenceByField: a map from
these field names to EvidenceRef[]. Evidence-empty skills is an empty extracted
set, not evidence that the role requires no skills.

## DATA-003 — Search, source, and policy configuration

These records MUST be revisioned immutable configurations.

| Record | Additional fields |
|---|---|
| SearchDefinition | name: Text; enabled: boolean; criteria: Criterion[]; sourceRefs: Ref[]; limits: ScanLimits; schedule: Schedule; applicationPolicyRef: Ref or null |
| SourceConfiguration | name: Text; startUrl: URL; allowedOrigins: Origin[]; browserProfileId: UUID; enabled: boolean; supportStatus: unverified/fixture_verified/user_verified/known_restriction; supportNote: Text or null |
| ApplicationPolicy | name: Text; enabled: boolean; mode: review_required/automatic; eligibleSearchIds: UUID[]; destinationOrigins: Origin[]; approvedResumeRefs: ArtifactRef[]; allowGeneratedCoverLetter: boolean; maxSubmissionsPerDay: integer 1..100; timezone: valid IANA zone |

ScanLimits = {maxResultPages: integer 1..100, maxCandidates: integer 1..1000,
maxActiveSeconds: integer 60..14400, maxNoProgress: integer 1..10}; defaults are
10, 100, 1800, and 3. Schedule = {enabled: boolean, intervalMinutes: integer
15..10080}; default false and 360. Runtime nextDueAt is not configuration.

Source startUrl origin MUST belong to allowedOrigins. Wildcard origins are not
supported. Application navigation to an external ATS requires the destination
origin to be allowed for the application; discovery navigation is limited to
source origins. A policy can be saved disabled before documents exist; enabling
automatic mode requires at least one eligible search, destination, and approved
resume. No policy defaults to allowing all sites.

New policy defaults are enabled=false, mode=review_required, empty eligible-search,
destination, and resume arrays, allowGeneratedCoverLetter=true, cap=5, and the
confirmed application timezone. A null search policy means review_required.
Changing a policy's timezone applies to future intents only; existing quota rows
retain their original policy date and timezone.

## DATA-004 — Scan and operational records

ScanRun MUST be mutable and contain searchRef: Ref, sourceRefs: Ref[], trigger:
manual/scheduled, state: queued/running/paused/completed/partial/failed/cancelled,
startedAt and finishedAt: Instant or null, pauseRequested: boolean,
cancelRequested: boolean, sourceRuns:
SourceProgress[], counts: RunCounts, and baseExportId: UUID or null.

SourceProgress = {sourceRef: Ref, state: queued/running/paused/completed/partial/
failed/cancelled, checkpointId: UUID or null, resultPages: integer>=0,
candidates: integer>=0, activeMilliseconds: integer>=0, stopReason: error code
or null}. RunCounts = {encountered, matched, rejected, needsReview, previouslySeen,
newEligible}, all integers >=0, with counts derived from durable encounters.
They are not necessarily a partition: matched listings can also be previouslySeen.

The following supporting records MUST be persisted.

| Record | Fields in addition to common fields |
|---|---|
| WorkItem (mutable) | kind: WorkKind; entityId: UUID; state: queued/leased/waiting/completed/failed/cancelled; availableAt: Instant; ownerId: UUID or null; leaseUntil: Instant or null; fence: integer>=0; attempts: integer>=0; checkpoint: validated kind-specific object or null; lastError: ErrorDetail or null |
| ScheduleCursor (mutable) | searchId: UUID; nextDueAt: Instant; lastEnqueuedAt: Instant or null |
| BrowserProfile (mutable) | name: Text; storageKey: opaque Text; status: available/in_use/needs_login; lastUsedAt: Instant or null |
| Operation (mutable) | kind: WorkKind; targetId: UUID; state: queued/running/waiting/succeeded/failed/cancelled; workItemId: UUID or null; resultRef: {kind: scan/application/resource_index/export/model_diagnostic/intervention,id:UUID} or null; error: ErrorDetail or null |
| IdempotencyRecord (immutable) | principalId: UUID; method: Text; route: Text; key: Text; bodyHash: Hash; httpStatus: integer; response: validated response envelope |

Scan checkpoints MUST contain sourceRef, currentUrl, visited canonical URLs,
pending detail URLs, completed encounter IDs, active time, and browser generation.
Prepared form checkpoints MUST contain the application revision and last verified
step, never assume that old element handles survive restart. JSON blobs MUST
validate against their named contract before persistence.

WorkKind is scan/prepare_application/reindex/export/model_diagnostic/pause_run/
resume_run/cancel_run/cancel_application/open_intervention. Control work contains
{targetRevision:Revision,requestedAt:Instant}; export work contains
{batchId:UUID}; diagnostic work contains {settingsRevision:Revision}; resource
index work contains {completedResourceRefs:Ref[],pendingRelativePaths:Text[]}.
An application checkpoint is {preparedRevision:integer>=0,lastVerifiedStep:
Text or null,browserGeneration:integer or null,activeMilliseconds:integer>=0,
actionCount:integer>=0}. A scan checkpoint has the fields described above with
visitedCanonicalUrls/pendingDetailUrls:URL[], completedEncounterIds:UUID[],
activeMilliseconds:integer>=0, currentUrl:URL or null, and
browserGeneration:integer or null.

Control commands MUST set request flags atomically when enqueued. The worker
checks them between actions; they do not wait behind a browser workflow holding
the lease they intend to pause. Control operations complete only when the worker
acknowledges the corresponding state.

## DATA-005 — Listings, opportunities, and encounters

Listing MUST use a stable id with immutable content revisions. Its header holds
firstSeenAt, lastSeenAt, opportunityId, sourceNamespace (normalized source origin),
sourceJobId: Text or null, canonicalUrl: URL, and firstEncounterId: UUID.
Each revision holds originalUrl: URL, applicationUrl: URL or null,
employerRequisitionId: Text or null, normalizedJob: NormalizedJob with description
nullable after permitted pruning, contentHash: Hash, and availability:
open/closed/unknown. Identity aliases are persisted separately and unique.

Opportunity MUST be mutable: primaryListingId: UUID, state: active/closed/merged,
mergedIntoId: UUID or null, noveltyState: pending/eligible/consumed/ineligible,
noveltyEncounterId: UUID, exportedBatchId: UUID or null. An opportunity cannot be
its own merge target. Listing associations use foreign keys, not embedded copies.

Encounter MUST be immutable: runId: UUID, sourceRef: Ref, listingRef: Ref,
observedAt: Instant, wasKnownBeforeEncounter: boolean, firstDiscoveryLineage:
boolean. Assessment linkage and resolution are separate records so the original
encounter stays immutable. Uniqueness is (runId, listingId, contentHash).

OpportunityRelation MUST be mutable: leftId: UUID, rightId: UUID, kind:
possible_duplicate/possible_repost/confirmed_duplicate/distinct, evidence:
EvidenceRef[], resolvedBy: Actor or null, resolvedAt: Instant or null. Unordered
pairs use sorted IDs for uniqueness. A deterministic merge records identity
evidence and an event; it MUST not erase either listing or earlier application.
The record also MUST contain resolutionReason: Text or null. resolvedBy,
resolvedAt, and resolutionReason are either all null for an unresolved relation
or all present for a recorded resolution. Self-relations are invalid.

## DATA-006 — Assessments

MatchAssessment MUST be immutable and contain listingRef, searchRef, encounterId:
UUID, decision: match/reject/needs_review, criteria: CriterionResult[],
summary: Text, contentHash: Hash, matcherVersion: Text, promptVersion: Text,
modelId: Text or null, modelConfigHash: Hash or null, resolvedFromId: UUID or null,
actor: Actor. Deterministic-only rejections may have null model fields.

CriterionResult = {criterionId: UUID, outcome: pass/fail/unknown/conflict,
reason: Text, evidence: EvidenceRef[]}. Missing data may have no evidence but MUST
have a reason. Match requires every required criterion to pass; any required fail
rejects; otherwise required unknown/conflict requires review. Preferred failures
affect explanation and ordering, not eligibility.

A manual resolution creates another immutable assessment with resolvedFromId.
It MUST include criterion-level changes and reasons. There is no undocumented
force-match boolean that bypasses unresolved required criteria.

## DATA-007 — Resources, artifacts, and profile

ResourceDocument MUST have stable id and immutable versions: relativePath: Text,
mediaType: Text, sizeBytes: integer, sha256: Hash, extractionState:
pending/extracted/unsupported/failed/missing, textArtifactId: UUID or null,
segments: Segment[], error: ErrorDetail or null. Segment = {id: Text, locator:
Text, text: Text}; locators are paragraph, page, or JSON-pointer descriptions.
Paths MUST remain within the resource root after realpath resolution.

Artifact MUST be immutable: kind: resource_snapshot/resume/cover_letter_text/
cover_letter_pdf/export/diagnostic/submission_evidence, storageKey: opaque Text,
displayName: Text, mediaType: Text, sizeBytes: integer>=0, sha256: Hash,
sensitivity: personal/public,
createdBy: Actor, expiresAt: Instant or null. Mutable availability is tracked
separately as present/missing/expired. Hash addresses content, not permissions.
displayName is a sanitized filename with no directory components; it is used for
downloads and uploads and grants no filesystem access. Generated documents use
cover-letter.txt or cover-letter.pdf; existing resumes preserve a sanitized source
basename. Text extraction artifacts use kind=resource_snapshot and text/plain.

ApplicantProfile MUST be revisioned: factRefs: Ref[], defaultResumeRef:
ArtifactRef or null, alternativeResumeRefs: ArtifactRef[], narrativeInstructions:
Text or null. ApplicantFact MUST be revisioned: key: Text, value: FactValue,
status: proposed/confirmed/conflicted/stale/rejected, provenance: EvidenceRef[],
confirmedAt: Instant or null, confirmedBy: Actor or null, supersedes: Ref or null,
sensitive: boolean. Keys and value types are defined in chapter 06.

FactValue is a discriminated union: {type: text,value:Text}, {type: boolean,
value:boolean}, {type: date,value:Text,precision:year/month/day},
{type: text_list,value:Text[]},
or {type: number,value:finite number,unit:Text}. Structured histories use separate
facts keyed by stable employment/education entry IDs, not arbitrary unvalidated
objects. A fact with value=false is known false, not unknown.
Date values MUST match their precision: YYYY, YYYY-MM, or YYYY-MM-DD, with a valid
calendar value. A source giving only a month must not acquire an invented day.
Forms demanding finer precision create needs_input; fields accepting the known
precision may use it directly.

## DATA-008 — Application and authorization records

ApplicationAttempt MUST be mutable: opportunityId: UUID, listingRef: Ref,
searchRef: Ref, assessmentId: UUID, policyRef: Ref or null, profileRef: Ref,
state: queued/preparing/ready/needs_input/needs_review/submitting/submitted/
submission_unknown/failed/cancelled/closed, preparedRevision: integer>=0,
destinationUrl: URL or null, formSignature: Hash or null, answerRefs: UUID[],
attachmentRefs: ArtifactRef[], approvalId: UUID or null, intentId: UUID or null,
blockingReasons: error-code[], retryable: boolean, startedAt/finishedAt:
Instant or null. A uniqueness guard by resolved opportunity lives separately.

PreparedAnswer MUST be immutable: applicationId: UUID, preparedRevision:
Revision, fieldKey: Text, fieldKind: enum in AGENT-002, value: string/boolean/
string[], sourceFactRefs: Ref[], sourceEvidence: EvidenceRef[], origin:
profile/generated/user, claimRefs: Claim[], validationState: valid/blocked.
Claim = {text: Text, evidence: EvidenceRef[]}. Sensitive answers must have an
explicit confirmed response preference.

ApplicationApproval MUST be immutable: applicationId: UUID, preparedRevision:
Revision, snapshotHash: Hash, approvedBy: Actor, approvedAt: Instant. Revocation
is a separate event; never mutate an approval to fit a changed application.

SubmissionIntent MUST be immutable: applicationId: UUID, preparedRevision:
Revision, snapshotHash: Hash, targetOrigin: Origin, observationId: UUID,
elementRef: Text, policyRef: Ref or null, approvalId: UUID or null, quotaDate:
YYYY-MM-DD or null, createdAt: Instant, fencingGeneration: integer. At least one
valid authority (current automatic policy or current user approval) is required.

SubmissionEvidence MUST be immutable: applicationId: UUID, intentId: UUID or null,
kind: confirmation_page/application_status/user_resolution, referenceNumber:
Text or null, destinationUrl: URL, evidence: EvidenceRef[], artifactRefs:
ArtifactRef[], conclusion: submitted/not_submitted/unknown, actor: Actor.
Human submissions without an agent intent are marked user_resolution.

## DATA-009 — Interventions and audit events

InterventionTask MUST be mutable: targetKind: scan/application/resource,
targetId: UUID, reasonCode: error code, requestedAction: Text, state:
open/in_progress/resolved/cancelled, browserGeneration: integer or null,
resolution: {kind: supplied_input/approved/rejected/retry/unsupported/
submitted/not_submitted, note: Text, actor: Actor} or null, resolvedAt: Instant
or null. A browser connection disappearing does not resolve this record.

AuditEvent MUST be immutable: sequence: increasing integer, type: namespaced
Text, actor: Actor, entityKind: Text, entityId: UUID, correlationId: UUID,
details: allowlisted redacted object. Event types include search.revised,
scan.started, identity.merged, assessment.resolved, fact.confirmed,
application.approved, submission.intent_created, submission.resolved, and
export.written. Events MUST reference revisions rather than repeat personal text.

## DATA-011 — Constraints, transactions, and leases

SQLite MUST enable foreign keys on every connection, WAL journaling, synchronous
FULL, and a 5000 ms busy timeout. Network calls MUST not occur inside database
transactions. Use short immediate write transactions for claims, identity merges,
intent creation, and export membership. Busy expiration returns STORAGE_BUSY,
not a partially committed command.

Required uniqueness: normalized source namespace plus non-null source job ID;
canonical URL alias; (run, listing, content hash) encounters; (entity, revision)
snapshots; one active run per search including paused runs; one submission guard
per resolved opportunity; one base export per run; one initial novelty export
membership per opportunity; (run, supplemental sequence); idempotency scope.

Identity merging MUST atomically update current aliases, listing associations,
guards, and export eligibility to the surviving identity. Immutable encounters,
assessments, export memberships, and submitted snapshots retain their original
references, resolved through the surviving-identity redirect on current reads.
If both identities have submission history,
preserve both attempts and block further submission pending reconciliation. Never
rewrite an immutable export to conceal an earlier uncertain identity.

## DATA-012 — Migrations, examples, and retention

Migrations MUST be ordered, checksummed, and applied under a single startup lock.
Unexpected checksum changes or a newer database schema block writes. No automatic
destructive downgrade is supported. Each migration requires a fixture upgrade
test and backup/restore notes. Foreign keys MUST restrict accidental deletion of
referenced snapshots.

Valid examples: a confirmed boolean work-authorization fact with value=false;
a listing with unknown salary=null; two listings on different hosts sharing a
verified employer requisition identity. Invalid examples: minHours=30/maxHours=20;
internship stored as an employment arrangement; automatic policy without an
approved resume; mutable rewriting of a submitted answer; lease renewal by an old
fence value. All MUST fail contract or domain validation as appropriate.

Rejected listing descriptions MAY be pruned once assessment summaries, evidence
excerpts, hashes, and identity are committed. Matching/review descriptions remain.
Configuration revisions, confirmed fact history, submission artifacts, and identity
records MUST remain while referenced. User dismissal is not record deletion.

An immutable evidence segment MUST be retained even when its larger source
observation expires or a rejected description is pruned. Facts entered by the user
create fact-kind evidence segments referencing their confirmed revision. Secret
generation is a one-way digest used only for revocation comparison, never a
reusable administrator credential. Control/result records and side-table changes
MUST participate in the owning command transaction.

### Per-record example cases

These are illustrative field-level examples; all unmentioned mandatory fields
must still be present in a complete record. Each invalid case MUST fail schema,
domain, or referential validation rather than be silently coerced.

| Record | Valid case | Invalid case |
|---|---|---|
| SearchDefinition | One required title, preferred weekly hours 16..24, disabled schedule | No title criterion or duplicate criterion kinds |
| SourceConfiguration | Start origin is explicitly in allowedOrigins | Start URL at an unlisted origin |
| ApplicationPolicy | Disabled review policy with empty resume choices | Enabled automatic policy with no approved resume |
| ScanRun | Partial run with a source LIMIT_REACHED and durable results | Completed run whose only source remains running |
| WorkItem | Current fence renews its unexpired lease | Earlier owner renews after a new fence was issued |
| ScheduleCursor | Next boundary lies in the future after one catch-up | Downtime enqueues every historical interval |
| BrowserProfile | Dedicated opaque storage key, needs_login status | User-supplied host absolute path used as storage key |
| Operation | Waiting operation references its persisted work item | Succeeded operation whose export is still unwritten |
| IdempotencyRecord | Same key/body returns original operation | Same key substituted with a different body hash |
| Listing | Unknown employer=null and retained canonical job identity | Unknown employer invented from site branding |
| Opportunity | Pending first lineage has no exportedBatchId | Opportunity merges into itself or forms a merge cycle |
| Encounter | Repeated card reuses the same run/listing/hash encounter | Duplicate row violating the encounter key |
| OpportunityRelation | Two different IDs with evidence and a reviewed distinct resolution | A resolved relation with no actor or reason |
| MatchAssessment | Required unknown hours produces needs_review | Match with a required criterion outcome=unknown |
| ResourceDocument | Changed bytes create revision 2 at the same relative path | Existing version overwritten without changing its hash |
| Artifact | Present immutable resume whose byte hash matches | Storage path escaping its root |
| ApplicantProfile | Default resume is a verified resume artifact | Default resume points to a diagnostic screenshot |
| ApplicantFact | Confirmed false sponsorship requirement with explicit provenance | Proposed fact treated as confirmed without user action |
| ApplicationAttempt | Ready attempt has validated prepared revision | Submitting attempt with no committed intent |
| PreparedAnswer | Boolean checkbox value with source fact reference | Answer mapped to a nonexistent fieldKey |
| ApplicationApproval | Hash and revision match reviewed answers | Approval reused after changing an attachment |
| SubmissionIntent | One authority and one current observation | Intent points at a stale browser generation |
| SubmissionEvidence | Application-specific receipt with supporting segment | Generic HTTP 200 presented as confirmation |
| InterventionTask | Open task persists after viewer disconnect | Resolved task with null resolution |
